# Нагрузочное тестирование бэкенда

Как проверить, сколько нагрузки выдерживает `app.carreports.ru` (JSON-RPC 2.0
поверх HTTPS POST). Инструмент — [k6](https://k6.io) (`brew install k6`).

## ⚠️ Прочитать до запуска

`app.carreports.ru` — **прод**, и он хрупкий:

- Один синхронный `RunBatchLegalReview` уже клал **весь** воркер-пул на ~2 мин
  (nginx отдавал 504 всем; инцидент 2026-06-10). Нагрузочный тест штатных
  методов может дать тот же эффект под нагрузкой.
- Поэтому: **запускать только в согласованное с бэкенд-девом окно**, пока он
  смотрит на серверные метрики (CPU / RAM / размер воркер-пула / логи nginx).
  Без серверной стороны видна только половина картины: «упало» — а почему,
  непонятно.
- Идеально — попросить у дева **staging-инстанс** и гонять по нему
  (`-e BASE_URL=https://staging...`), тогда прод вообще не трогаем.

Скрипт `k6_rpc_read.js` намеренно бьёт **только read-методы**. Он НЕ трогает:
- платные ApiCloud-проверки (каждый вызов — реальные деньги);
- `Storage.Auth` / `AuthVerify` (инициируют реальный звонок на телефон);
- write-методы (`CreateRequest`, S3 PUT, и т.п. — пишут в прод-базу).

## Токен

Нужен свежий access-JWT (живёт ~12 ч). Взять из dev-заметки или обновить:

```bash
RT='<refresh-token>'
curl -sS -X POST https://app.carreports.ru -H 'Content-Type: application/json' \
  -d "{\"jsonrpc\":\"2.0\",\"id\":1,\"method\":\"RefreshToken\",\"params\":{\"refreshToken\":\"$RT\"}}"
```

Ответ вернёт новые `accessToken` + `refreshToken`. Скрипт сам проверит `exp`
токена в `setup()` и упадёт с понятной ошибкой, если он просрочен.

## Этапы (по возрастанию риска)

Запускать по порядку, между этапами смотреть на серверные метрики.

```bash
export AT='<access-token>'

# 1. Smoke — 1 пользователь, 30с. Проверить, что сценарий вообще ходит.
k6 run -e TOKEN=$AT -e SCENARIO=smoke    loadtest/k6_rpc_read.js

# 2. Baseline — 10 RPS, 5 мин. Точка отсчёта по латентности (p95).
k6 run -e TOKEN=$AT -e SCENARIO=baseline loadtest/k6_rpc_read.js

# 3. Ramp — ступени 10→150 RPS. САМ остановится, когда ошибок >5%.
#    «Колено», на котором p95 уезжает / растут ошибки, и есть потолок.
k6 run -e TOKEN=$AT -e SCENARIO=ramp     loadtest/k6_rpc_read.js

# 4. Soak — 15 RPS, 45 мин. Утечки памяти и деградация со временем.
k6 run -e TOKEN=$AT -e SCENARIO=soak     loadtest/k6_rpc_read.js
```

Флаги:
- `-e RECONNECT=1` — новый TCP+TLS на каждый запрос (так ведёт себя мобильное
  приложение — оно шлёт через top-level `http.post` без пула соединений).
  Без флага k6 держит keep-alive (поведение web-клиента). Полезно прогнать оба
  и сравнить: разница покажет цену отсутствия общего `http.Client` на мобиле.
- `-e BASE_URL=https://staging...` — гнать по staging вместо прода.

## Что мерить и как читать

k6 сам печатает по итогу:
- **`http_req_duration` p95/p99** — латентность. Тёплый бэк отвечает ~0.4–0.5с;
  порог в скрипте p95 < 3с. Уезжает вверх под нагрузкой = близко к потолку.
- **`http_req_failed`** — доля транспортных ошибок (таймаут / 5xx / reset).
  Стоп-кран: >5% (после 30с прогрева) гасит тест.
- **`rpc_app_error`** — своя метрика: HTTP 200, но RPC-ответ не `ok`. Ошибки
  уровня приложения nginx-ом не считаются — без неё их не увидеть.
- **`iterations` / `http_reqs`** — фактический достигнутый RPS.

Ответ на «сколько выдержит» = максимальный RPS ступени ramp, на котором p95
ещё в норме и ошибок <1%.

## Что уже известно без теста (аудит 2026-06-10)

Отдать деву как гипотезы узких мест — ramp, скорее всего, упрётся сюда:
- холодный первый хит спящих методов — до 41–47с (`GetSpecialistReport`);
  повторные — 0.4–0.5с. Скрипт делает прогрев в `setup()`, чтобы это не
  засчиталось нагрузке;
- сервер **не сжимает** ответы (gzip игнорируется) — лишний трафик;
- синхронный ApiCloud-sync душит весь воркер-пул (главный подозреваемый);
- у ~10% ApiCloud-джобов нет reaper'а — застревают в pending навсегда.
