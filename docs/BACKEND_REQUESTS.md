### 🔴 P0: Серверная intake-job для распределения файлов в фоне

**Симптом.** Нативные `URLSession` / `WorkManager` могут закончить PUT в S3
при заблокированном экране, но следующий шаг сейчас — синхронный
`AiQueue.ChatCompletions` из Flutter. iOS замораживает Dart-isolate, поэтому
ИИ-распределение не стартует до открытия приложения. Фоновая задача iOS не
даёт гарантированного времени на vision-вызов длительностью до 150 секунд.

**Нужно.** Intake должен становиться серверной идемпотентной job **до** начала
нативной заливки. Backend ждёт появления ожидаемых S3-объектов (S3 event либо
poll/head), сам выдаёт временные view URL, вызывает AiQueue и хранит результат.

Предлагаемый контракт:

1. `Storage.CreateMediaIntakeJob({clientDraftId, items, taxonomy})` →
   `{jobId, status}`. `clientDraftId` — UUID/idempotency key в scope пользователя.
2. `items` для фото/документа: `{hash, s3Key, mimeType, originalName}`; для видео:
   `{hash, mimeType:"video/*", originalName, durationMs, frames:[{s3Key,index,timeMs}]}`.
3. `taxonomy` содержит только разрешённые разделы, группы и элементы осмотра;
   prompt/cliche лучше формировать на backend по версионируемому шаблону.
4. Job переходит `waiting_uploads → processing → completed|failed`; отсутствующие
   объекты ждёт до TTL temp-хранилища, повторный вызов с тем же `clientDraftId`
   не создаёт вторую платную обработку.
5. `Storage.GetMediaIntakeJob({jobId})` возвращает
   `{status, items:[{hash,section,group,element,documentKind,documentData}],error?}`.
6. По завершении желательно отправлять `Notification.Push`; приложение также
   опрашивает job при открытии и применяет результат к локальным оригиналам по hash.

**Почему не native callback клиента.** Callback загрузчика исполняется в отдельном
isolate на Android, не имеет надёжного доступа к состоянию/плагинам приложения, а
на iOS получает ограниченное системное время. Он подходит для короткого HTTP
подтверждения upload, но не для пачек vision, извлечения СТС/ПТС и сохранения
согласованного результата.

### 🔴 P0 ИНЦИДЕНТ (2026-07-05): AiQueue не достукивается до провайдера codex.sale — все AI-функции лежат

**Симптом в приложении** (включая прод-билд RuStore 1.0.0+3): любая

отправится при появлении сети», при этом запрос считается выполненным

**Живое воспроизведение 2026-07-05 ~16:50 UTC** (POST `https://ai.carreports.ru`,
`AiQueue.ChatCompletions`, обе модели `gpt-5.4` и `gpt-5.5`, стабильно
на повторах, ~10.2 с на ответ — похоже на connect-timeout 10 с):

```json
{"response":"success","fromMethod":"AiQueue.ChatCompletions","result":[],

```

При этом `AiQueue.Models` / `AiQueue.Health` отвечают нормально — лежит
только исходящее соединение к LLM-upstream `codex.sale:443` (DNS
резолвится, TCP не устанавливается: файрвол/маршрутизация с сервера или
сам codex.sale недоступен).

**Просьбы:**

1. Восстановить связность `ai.carreports.ru` → `codex.sale:443`
   (проверить с самого сервера: `curl -v --connect-timeout 12 https://codex.sale`).
2. Отдавать такие фейлы как ошибку, а не `response:"success"` с пустым
   `result:[]` — клиент при `success` поле `errors` не читает и
   показывает пользователю сбивающее «пустой ответ» вместо
   «сервис недоступен».

### 🔴 P0: Файлы в заявке

**Use case.** Компания при создании заявки должна прикреплять файлы к заявке
для специалиста: фото, PDF, документы, таблицы и другие обычные файлы.
Видео прикладывать нельзя.

**Сейчас.** Live `Doc` на 2026-05-21 показывает:

- `Storage.CreateRequest` не принимает `files` / `attachments`;
- `Storage.GetRequest` не возвращает файлы заявки;
- отдельного метода вроде `Storage.AttachRequestFile` /
  `ObjectStorage.Request.*` нет;
- общий `ObjectStorage.*` завязан на `reportNumber` и временный `temp`, поэтому
  его нельзя безопасно использовать как постоянные вложения заявки.

**Нужно.** Добавить серверный контракт для постоянных файлов заявки.
Предпочтительный вариант:

1. `ObjectStorage.Request.InitiateMultipartUpload({requestId?, filename, contentLength, contentType})`
2. `ObjectStorage.Request.GetPartUploadUrls({filename, uploadId, partCount})`
3. `ObjectStorage.Request.CompleteMultipartUpload({filename, uploadId, parts})`
4. `Storage.CreateRequest({ ..., attachments: [...] })`
5. `Storage.GetRequest` возвращает `attachments: [{id, filename, contentType, contentLength, viewUrl?}]`
6. `ObjectStorage.Request.GetViewUrl({attachmentId})` для приватного просмотра.

**Frontend rules.**

- Запрещаем `contentType` с префиксом `video/`.
- На клиенте дополнительно фильтруем типы файлов, но финальная валидация должна
  быть на backend.
- Вложения должны быть доступны компании и назначенному специалисту.
- Если заявка ещё не создана, нужен `draftUploadToken` / временная зона хранения,
  которую backend привяжет к заявке после `CreateRequest`.

### 🔴 P0: Аватарка профиля — два блокера в S3-флоу

Клиентский флоу загрузки реализован и протестирован end-to-end
(2026-05-20, sub=2, role=company, platform=web). Шаги 1–4
**работают**, но финал и рендеринг падают на бэкенде.

**Что работает ✅**

| Шаг | Метод | Результат |
|---|---|---|
| 1 | `ObjectStorage.Profile.InitiateProfileMultipartUpload` | ok — `uploadId`, `key=app/user/2/profile/avatar.png`, `publicUrl` |
| 2 | `ObjectStorage.Profile.GetProfilePartUploadUrls` | ok — presigned PUT URL |
| 3 | PUT в S3 (`s3.regru.cloud`) | ok — `ETag "2cd8bde4…8f"` |
| 4 | `ObjectStorage.Profile.CompleteProfileMultipartUpload` | ok — `publicUrl`, `contentSize: 70` |

---

#### Баг 1 — `Storage.UpdateProfile({urlAvatar})` зависает

Запрос **специфичен для поля `urlAvatar`**: висит >25s, `0 bytes received`.
Любое другое поле обрабатывается мгновенно.

```jsonc
// ❌ висит (timeout 25s, 0 байт)
{"method":"Storage.UpdateProfile","params":{"urlAvatar":"https://s3.regru.cloud/reports/app/user/2/profile/avatar.png"}}

// ✅ возвращается за 0.68s
{"method":"Storage.UpdateProfile","params":{"city":"Москва"}}
```

**Гипотеза.** Хэндлер `urlAvatar` синхронно валидирует URL (HEAD/GET
на S3, чтобы проверить что объект существует в папке юзера), напарывается
на 403 (см. Баг 2) и виснет в ретраях/ожидании без таймаута.

**Нужно.** Хэндлер `urlAvatar` не должен блокироваться: ограничить
проверку таймаутом, не делать сетевой fetch на S3 (достаточно проверить
что URL-префикс == `app/user/{userId}/profile/`), вернуть ответ.

---

#### Баг 2 — `publicUrl` не публично читается (403)

«Публичный» URL из Initiate/Complete отдаёт **403 AccessDenied**:

```
GET https://s3.regru.cloud/reports/app/user/2/profile/avatar.png
→ HTTP/1.1 403 Forbidden
  <Error><Code>AccessDenied</Code><BucketName>reports</BucketName></Error>
```

Клиент рендерит аватар через `CachedNetworkImage` — обычный GET **без
авторизации**. С 403 он всегда падает в fallback на инициалы, картинка
не покажется никогда.

**Нужно (на выбор):**

A. Сделать `app/user/*/profile/*` публично-читаемым (bucket policy /
   public-read ACL) — тогда `publicUrl` действительно публичный, как
   обещает имя поля.

B. Если объекты должны оставаться приватными — добавить
   `ObjectStorage.Profile.GetProfileViewUrl({filename})` → presigned GET
   URL, и в `GetProfile.urlAvatar` отдавать presigned-ссылку (с TTL),
   а не «голый» S3-URL.

Вариант A проще для клиента (URL стабильный, кэшируется). Вариант B —
если приватность аватарок принципиальна.

### 🟡 P1: Дедуп платных ApiCloud-проверок (конвертер VIN↔госномер)

**Сейчас (ветка `cnc` на 2026-06-22, `wswalker`).** Каждый
`Storage.RunBatchLegalReview` БЕЗУСЛОВНО создаёт новый `LegalReviewCheck`
(Pending) → NATS-джоб → платный HTTP-вызов ApiCloud (1,7 ₽ за запрос
`api_cloud_converter_search` — тариф из API_CLOUD_TEST_REPORT.md; «3,4» в
прежней редакции было «Итого» той таблицы за два тестовых прогона дева). Повторный запрос того же VIN/госномера — новое
списание, хотя результат уже лежит в БД:
`src/Service/DoctrineService/Entity/LegalReview/LegalReviewCheck.php` хранит
`vehicle_vin`, `vehicle_gos_number`, `check_type`, `status`,
`response_normalized`, `executed_at`, и под выборку «последний чек по
VIN/номеру + типу» уже созданы индексы `idx_lrc_vin_type_executed` и
`idx_lrc_gos_number_type_executed`. В
`LegalReviewCheckRepository` есть неиспользуемый `findLatestForStepAndType()`.

**Use case.** Специалист определяет авто по VIN/госномеру в шаге «Автомобиль».
Один и тот же номер закономерно вводится повторно: пересоздание черновика,
другое устройство, другой специалист той же компании, повторная инспекция
той же машины. Связка VIN↔госномер меняется редко — повторная оплата
идентичного ответа ApiCloud не даёт ничего.

**Нужно.** В `QueueBatchApiCloudLegalReviewUseCase::queue()` перед созданием
Pending-чека искать последний `Success`-чек с тем же
(`vehicle_vin`|`vehicle_gos_number`) + `check_type`:

1. Если найден и свежее TTL (предложение: 30 дней для конвертера; для
   залога/такси/ГОСТ — короче, они изменчивее) → вернуть его
   `response_normalized` в батче сразу (`status: success`), НЕ дёргая ApiCloud
   и НЕ списывая деньги.
2. Если по тому же входу есть живой `Pending` (моложе N минут) → привязать к
   батчу существующий джоб вместо постановки нового (закрывает и дубли-джобы,
   и накопление «вечных pending»).
3. Опционально: флаг `forceRefresh: true` в `RunBatchLegalReview`, чтобы фронт
   мог явно перезапросить свежие данные, минуя кэш.

**Frontend context.** Клиент уже делает всё, что возможно со своей стороны
(single-flight, переиспользование оплаченного `batchNumber` 24 ч, с 2026-07-05
— локальный персист терминального результата конвертера, 30 дней). Но
клиентский кэш не покрывает другое устройство/другого пользователя и чистку
локального хранилища — глобальный дедуп возможен только на бэке, и все данные
для него уже в `legal_review_check`.

### 🟡 P1: «Материалы проверки» — 2 бага корректности LegalReview (репорт пользователя 2026-07-15)

Репорт: (а) «загрузка очень долгая и по сути бесконечная, не может проверить
всё»; (б) на проверке такси всплывает сырое «gosNumber% forbidden symbols
present». **Бэк-дев подтвердил и починил свою часть (а) 2026-07-15** —
live-проверка после фикса: батч `LEG-A671015` (17:22 UTC) исполнился весь за
11с, summary `{total:4, completed:4, pending:0, failed:0}`. Разбор
оставшегося по ветке `ucs` `wswalker` + live-данным:

**Баг 1 — `api_cloud_fgis_taxi_search` игнорирует VIN и молча шлёт пустой
запрос.** `ApiCloudLegalReviewProvider::buildTypeSpecificQuery()` для fgisTaxi
берёт ТОЛЬКО `gosNumber`; `array_filter` выкидывает пустую строку, и запрос
уходит в ApiCloud вообще без идентификатора → ApiCloud отвечает
`gosNumber% forbidden symbols present` (и это платный вызов). Клиент с
2026-07-15 всегда шлёт валидный кириллический номер или не запускает проверку,
но защита нужна и на бэке: если для fgisTaxi нет валидного `gosNumber`
(`^[А-ЯЁ0-9]+$`) — отклонять на валидации `RunBatchLegalReview` (или
конвертировать vin→номер через уже существующий converter), а не тратить
деньги на гарантированную ошибку.

**Баг 2 — ошибки ApiCloud с HTTP 200 маскируются под «не найдено» с сырым
message.** Live-пример (батч `LEG-A152604`, 2026-07-15 07:42): чек
`api_cloud_fgis_taxi_search` со статусом **`not_found`** и
`responseNormalized = {"found": false, "permit": null, "message":
"gosNumber: forbidden symbols p resent"}` — это ошибка валидации входа у
ApiCloud, а не «разрешение не найдено». `ApiCloudResponseNormalizer`
пробрасывает `message` как есть, `resolveStatus()` смотрит только на
HTTP-статус и `found` → сырой англоязычный текст доезжает до пользователя
под видом «не найдено». Нужно: признак ошибки в body (`status >= 400` /
известные тексты) → `LegalReviewCheckStatus::Error` + машиночитаемый
`errorCode` (например `invalid_gos_number`). Клиент с 2026-07-15 переводит
известные тексты на русский, но это хрупко — формат ApiCloud может
поменяться.

**Баг 3 — застрявшие `pending` до фикса: корень починен бэком 2026-07-15,
осталась подчистка хвоста.** Live-подтверждено (GetLegalReviewChecks,
2026-07-15 ~17:40 UTC): в БД лежат чеки в `pending` c `executedAt=null`,
которые уже никогда не завершатся, например батч `LEG-A423525`
(2026-07-14 22:03, **5/5 pending спустя ~20 ч**), `LEG-A152604` (2026-07-15
07:42, 2/5 pending), `LEG-A513070`, `LEG-A719006`, `LEG-A183419`,
`LEG-A275811`, `LEG-A810884`, `LEG-A180096`, `LEG-A485705`, `LEG-A932338`,
`LEG-A046236`. Просьба: одноразово перевести их в `error`
(`errorCode: timeout`) — черновики, к которым они привязаны, показывают
«проверки ещё выполняются» при каждом открытии (клиент честно таймаутит, но
результата не дождётся; пользователь может перезапустить «Сформировать» —
это новый платный батч). Плюс мини-reaper на будущее, чтобы новый сбой
воркера не копил такие же хвосты.

**Frontend context (сделано 2026-07-15):** стоп-условие поллинга больше не
зависит только от поля `status` чека (терминальность по
`responseNormalized`/`executedAt` + агрегатный `summary`), обрыв поллинга
после 3 подряд RPC-сбоев вместо молчаливого спиннера, ФГИС не запускается без
валидного номера, сырые сообщения провайдера переводятся на русский.

### 🟢 P2: Phone-flow для НЕ-штатных специалистов

**Сейчас.** `CreateRequest.assignedSpecialistId` валидирует что
специалист в моей компании. По `GetSpecialists(search:'+7...')`
можно найти НЕ-штатного спеца — но назначить его нельзя.

**Use case.** Компания хочет назначить заявку на специалиста по
номеру телефона, даже если он не в штате (фрилансер, разовый
исполнитель).

**Варианты решения (на выбор бэка):**

A. **Расширить `CreateRequest`** опц. полем `assignedSpecialistPhone`:
   - Если телефон совпал с зарегистрированным спецом → присвоить как assignee
   - Если совпал, но он не в компании → авто-инвайт в company перед assignment (или explicit error)
   - Если телефон не найден → SMS-приглашение «вас назначили на заявку №X, зарегистрируйтесь»

B. **Relax validation** в `assignedSpecialistId` — разрешить назначать
   на любого specialist, не только в моей компании. Тогда фронт сам
   получает userId через `GetSpecialists(search:phone)` и шлёт его.

C. **Invitation-первый flow:** добавить `Storage.InviteSpecialist({phone})`
   → создаёт user-record (если нет) + invitation → специалист принимает
   → попадает в компанию → потом обычное `CreateRequest`. Самый чистый,
   но требует SMS-инфры.

### 🟡 P1: Уведомления — чистка ленты и снижение объёма

**Сейчас (live `Doc` 2026-06-10).** Доступны только `Notification.GetNotifications`,
`Notification.MarkRead` (по ОДНОМУ, лишь `reminder`/`system`),
`Notification.ActionNotification`, `Notification.SendNotification`. Удаления,
архива и массовой отметки прочитанным НЕТ. Уведомления только меняют статус и
копятся; пользователь жалуется на «слишком много мусора».

**Use case.** Специалист/компания хотят быстро очистить ленту: отметить всё
прочитанным одним действием и убирать неактуальное.

**Нужно.**

1. `Notification.MarkAllRead({type?, before?})` — массовая отметка `read` для
   всех пассивных (`reminder`/`system`) pending за один вызов. Сейчас фронт
   вынужден циклически дёргать `MarkRead` по каждому id (N запросов) — это
   временный обход в `NotificationController.markAllRead()`.
2. Удаление/архив: `Notification.Delete({notificationId})` или
   `Notification.Archive(...)` (либо авто-истечение прочитанных `system` через
   N дней), чтобы лента не росла бесконечно.
3. **Снизить объём legal-уведомлений.** Бэкенд шлёт ОТДЕЛЬНОЕ system-оповещение
   на КАЖДУЮ ApiCloud-проверку (`legal_review_persisted`: zalog/taxi/gost/…) —
   это основной источник «мусора». Предложение: агрегировать проверки одного
   отчёта в ОДНО итоговое уведомление (или слать только при ошибке/важном
   результате). Конвертер (`api_cloud_converter_search`) фронт уже скрывает.

**Контекст (не баг бэкенда, для сведения).** Детали уведомления на клиенте
больше не показывают сырой payload (`event`, `*Id`, `requestType` и т.п.) —
выводится только курируемый человекочитаемый набор полей.

### 🟡 P1: Серверный кэш ApiCloud-ответов по VIN («tempo»)

**Use case.** Один и тот же VIN может проверяться повторно: пере-запуск

**Сейчас.** Проверено по коду wswalker (2026-07-05): кэша ApiCloud-ответов

**Нужно.** Кэш терминальных ответов ApiCloud на стороне бэка:

1. Ключ: `(checkType, vin)` (для fgis — `(checkType, gosNumber)`).
2. TTL ~24 часа (данные ГОСТ/залог/такси за сутки не протухают).
3. `RunBatchLegalReview` при cache-hit по всем типам не обращается к
   ApiCloud и не списывает средства — сразу отдаёт batch с готовыми
   результатами (или прежний `batchNumber`).
4. Кэшировать только терминальные статусы (`found` / `not_found`);

### 🔴 P1 (безопасность): `temp/` не скоупится по владельцу — IDOR на фото документов

**Находка (адверсариальное ревью 2026-07-08, подтверждено чтением
`ObjectStorage/GetTemporaryViewUrl.php` + `GetTemporaryUploadUrl.php`).**
Оба метода строят ключ `{reportNumber}/{filename}` прямой конкатенацией
клиентского ввода, гейтятся только `Auth::main` (любой авторизованный юзер)
и подписывают presigned URL на ЛЮБОЙ запрошенный ключ — без проверки, что
объект принадлежит этому пользователю. Папка `temp/` общая для всех.

Скан СТС/ПТС кладёт туда фото с ПДн владельца (ФИО, адрес, VIN, госномер).
**Фронт закрыл перебор клиентски** — имя файла теперь
`doc_scan_<мс>_<случайный hex>.jpg` (был только timestamp) + view-URL TTL
120с вместо суток. Но защита по-прежнему держится на неугадываемости имени.

**Нужно (defense-in-depth):** привязать `temp/`-ключи к `JWT.sub` на сервере
— писать/читать под `temp/<userId>/…` (сервер подставляет `sub`, не доверяя
клиенту) ИЛИ проверять владельца перед подписью. Тогда чужой ключ не
подпишется, даже если имя угадали.

### 🟡 P1: Notification.ActionNotification — ответ дольше клиентского таймаута

**Живой инцидент (2026-07-08).** Сотрудник принимает приглашение в штат →
клиентский таймаут (12с, поднят фронтом до 30с), при этом транзакция на
бэке УСПЕЛА закоммититься (статус + `users.company_id`) → повторный accept
получает `result.error = «Оповещение уже обработано.»`. Фронт добавил
reconcile-восстановление, но первопричина серверная:

1. HTTP-воркер ждёт внутренний IPC-ответ без таймаута
   (`MethodAbstract::publishChannel` — подписка на `…Resp` бессрочная);
   занятый/зависший DoctrineProcess держит соединение до клиентского
   таймаута. Просьба: серверный таймаут на IPC round-trip.
2. NATS-push и email-задачи публикуются ПОСЛЕ commit, но ДО ответа клиенту —
   при медленном NATS ответ задерживается, хотя данные уже записаны.
   Просьба: отвечать клиенту сразу после commit, рассылку — асинхронно.
3. У ошибки «Оповещение уже обработано.» нет машинного кода — фронт вынужден
   матчить русскую подстроку. Просьба: добавить стабильный код (например,
   `notification_already_processed`) рядом с текстом.

### 🟡 P1: Storage.CreateRequest(assignedSpecialistId) — ответ ~30 секунд

**Живой инцидент (2026-07-10).** Компания создаёт заявку с назначением на
специалиста → HTTP-ответ приходит через ~30 секунд (заявка при этом
создаётся успешно). Прямой вызов `CreateRequest` БЕЗ `assignedSpecialistId`
отвечает за ~173 мс — медленная именно ветка назначения.

**Подтверждено curl-замером 2026-07-10 ~17:47 UTC** (прогретый бэк,
sub=2/company, один и тот же payload, полный HTTP round-trip, без
какого-либо клиента/websocket):
- `CreateRequest` без назначения → `REQ-A515175`, **0.159с**;
- `CreateRequest` с `assignedSpecialistId:1` → `REQ-A280982`, **26.6с**;
- бонус: `CancelRequest` обычной заявки **0.149с**, а НАЗНАЧЕННОЙ —
  **13.5с** (уведомление специалисту об отмене → тот же путь).
Обе тестовые заявки отменены. Времена квантуются паузами retry-цикла
(1+4+9+10с): 26.6с ≈ полный проваленный цикл одного паблиша; 13.5с ≈
успех с 4-й попытки. Ищите в логах за это время `Nats connection failed,
attempt: N/5`.

**Первопричина (по коду wswalker).** В
`Action/Method/MainHttp/Storage/CreateRequest.php` после `$em->flush()` и
ДО ответа клиенту синхронно выполняется `notifySpecialistAssigned()`: 3
NATS-паблиша (realtime `Notify.Send` + email-джоб клиенту + email-джоб
специалисту через `AssignedRequestEmailNotificationUseCase`). Каждый
`NatsClient::publish` ждёт PubAck от JetStream и обёрнут в
`retryConnection()`: 5 попыток с паузами `min(attempt², 10)` =
1+4+9+10 = **24с пауз** + сами попытки (сокет-таймаут 1с) ≈ 25–30с.
Стабильные ~30с у клиента = один из паблишей стабильно фейлится все
5 попыток, исключение глотается `try/catch`, ответ уходит с опозданием.

**Важно про точку замера.** «Метод вернул результат» ≠ «HTTP-ответ ушёл
клиенту». `notifySpecialistAssigned()` выполняется ВНУТРИ `run()`, между
`$em->flush()` и `return` — замер «до готовности результата» (после flush)
эти ~30с не видит. Дальше результат едет к HTTP-воркеру через внутренний
канал `…Resp` (`MethodAbstract::publishChannel`, подписка бессрочная) и
только потом отдаётся клиенту. Мерить надо полный HTTP round-trip:
nginx `$request_time` / `$upstream_response_time` по запросу из приложения.
Фронт при этом ничего не ждёт, кроме этого HTTP-ответа: websocket-канал
уведомлений в флоу создания заявки не участвует.

**Как воспроизвести / проверить:**
1. Дёрнуть `Storage.CreateRequest` С `assignedSpecialistId` — ожидаемо ~30с.
2. В логах MainHttp-процесса в момент создания: `Nats connection failed,
   attempt: N/5` и/или `CreateRequest warning: failed to notify specialist`
   — покажут, какой subject буксует.
3. `nats stream ls` — существуют ли стримы/subjects для `notify_send` /
   `email_send`, жив ли JetStream (publish ждёт PubAck и падает, если
   стрима нет).

**Нужно:**
1. Отвечать клиенту сразу после commit; оповещение и email-джобы
   публиковать ПОСЛЕ ответа / асинхронно (то же, что п.2 в P1 про
   `ActionNotification` выше — корень общий).
2. Не держать retry-цикл с паузами до 24с внутри HTTP-обработчика —
   ретраи публикации уводить в фон.
3. Починить сам паблиш, который фейлится (side-effect: специалист сейчас,
   вероятно, недополучает realtime-пуш и/или email о назначении).

### 🟢 P2: Bulk-дамп каталога авто + версия каталога (для офлайн-кэша)

**Контекст.** Клиент теперь кэширует каталог авто локально (офлайн-выбор
марки/модели/поколения + строгий «только из каталога» ввод). Каталожные
методы отдают данные только по одному родителю: `GetBrand` (все ~90 марок
одним вызовом), `GetModelCar(brandId)`, `GetModelGeneration(modelCarId)`.
Полный обход каталога с устройства = 1 + ~90 + ~1000–2500 RPC. Клиент
делает это медленным фоновым триклом (0.8–2.5 r/s, resumable), чтобы не
упираться в nginx-лимит ~20 r/s, но по сути это N+1-краулер на каждое
устройство раз в TTL.

**Сейчас.** У каталожных сущностей (`Brand`, `ModelCar`, `ModelGeneration*`)
нет ни `updated_at`, ни версии, ни хэша (проверено по Entity/DTO wswalker)
— клиенту не по чему понять, что каталог не менялся, поэтому TTL = 7 дней
и слепой полный переобход.

**Нужно (любой из вариантов, лучше оба):**

1. `Storage.GetCarCatalogDump` — один метод, отдающий весь каталог
   (brands → models → generations с restylings/frames и топ-фото) одним
   gzip-ответом. Оценочно единицы МБ. Клиент заменит тысячи RPC одним
   вызовом раз в TTL.
2. Дешёвая инвалидация: `catalogVersion` (int/hash), меняющийся при любом
   импорте каталога — в ответе `GetBrand` или отдельным лёгким методом.
   Совпала версия → клиент вообще ничего не перекачивает.

**Пока не сделано:** клиент живёт на TTL 7 дней; нагрузка — сотни-тысячи
дешёвых read-RPC на устройство в неделю, размазанные триклом. Не срочно,
но дамп+версия убирают её почти в ноль.

### 🔴 P1 (юридическое, 152-ФЗ): реальное удаление аккаунта вместо деактивации

**Сейчас.** `Storage.DeactivateAccount` ставит только `is_active=false`
(`is_delete` не меняется), все персональные данные остаются навсегда.
При этом кнопка в приложении называется «Удалить аккаунт», а Условия
использования обещают удаление/обезличивание.

**Надо.** Ст. 21 152-ФЗ: по требованию субъекта / отзыву согласия оператор
обязан прекратить обработку и уничтожить или обезличить ПДн в течение
30 дней (кроме сведений, которые обязан хранить по закону). Apple-ревью
с текущей деактивацией УЖЕ ПРОЙДЕНО (подтверждено 2026-07-20), так что
store-блокера нет — задача остаётся юридической: риск это жалоба субъекта
в РКН, чьи данные «удалили», а они остались. Предложение: `Storage.DeleteAccount` (или
доработка текущего метода) — пометка `is_delete` + отложенное (до 30 дней)
уничтожение/обезличивание профиля (ФИО, телефон, email, аватар) и вычистка
ПДн из материалов, где нет законного основания хранить. Фронту достаточно
синхронного ack; сам процесс — асинхронный.

### 🔴 P1 (юридическое, 152-ФЗ): серверная фиксация факта согласия на ПДн

**Сейчас.** Согласие на обработку ПДн и принятие условий подтверждаются
чекбоксами только в UI; на бэке не сохраняется ничего. По ч. 1 ст. 9
152-ФЗ бремя доказывания получения согласия лежит на операторе —
при жалобе субъекта в РКН доказать нечем.

**Надо.** Принимать и хранить (в `Storage.Auth`/`AuthVerify` или отдельным
методом): телефон, версию текста согласия (напр.
`pdn_consent_version: "1.0-2026-07-02"`), версию условий, timestamp, IP.
Хранить и после удаления аккаунта — это доказательство, не операционные
данные. Фронт начнёт слать поля, как только бэк их примет (строгие DTO
сейчас не позволяют слать лишние ключи).
