# AiQueue · клиентская интеграция

Спецификация для клиентского кода Spark Joy / автоподборщика, описывающая
как пользоваться сервисом **AiQueue** (`https://aiqueue.ru.tuna.am`) для
формализации заметок по элементам автомобиля и сборки итоговой заметки по
отчёту.

Источник правды по API: live OpenRPC `AiQueue.Doc()` →
`docs/openrpc_aiqueue_doc_2026-04-24.json`.

---

## 1. Обзор

AiQueue — JSON-RPC 2.0 сервис AI-обработки. Клиент использует его в двух
сценариях:

1. **Per-element** — формализация заметки по одному элементу осмотра
   (например, «капот» / «двигатель» / «лобовое стекло»). Вход: сырой текст
   пользователя + опциональные фото/аудио + cliche (правила для AI). Выход:
   отформатированная заметка от AI.
2. **Final summary** — сборка итоговой заметки по всему отчёту. Клиент
   подтягивает истории всех per-element чатов, складывает их в общий
   контекст, открывает новый чат и получает финальный текст.

Каждый чат живёт в NATS KV ~6 часов (env `AI_QUEUE_CHAT_HISTORY_TTL_HOURS`,
TTL продлевается на каждой записи, не на чтении). После TTL история
теряется — клиент должен либо успеть собрать summary внутри окна, либо
быть готов к пустому ответу от `GetChatHistories`.

## 2. Endpoint и авторизация

| Параметр | Значение |
|---|---|
| Endpoint | `https://aiqueue.ru.tuna.am` |
| HTTP | `POST` |
| Content-Type | `text/plain;charset=UTF-8` *(не JSON — намеренно, см. ниже)* |
| Авторизация | JWT через query-параметр `?token=<jwt>` |
| Без авторизации | `AiQueue.Doc`, `AiQueue.Health` |

**Важно про Content-Type.** Сервер ожидает `text/plain`, не
`application/json`. Тело — это валидный JSON-RPC payload, но header не
выставлять как JSON, иначе сервер может отклонить.

**JWT claims, которые читает сервер**:
- `sub` — userId
- `role` — `admin | user | specialist`
- `exp` — UNIX-секунды

Тот же access-token, что используется для `Storage.*` (получаемый через
`Storage.AuthVerify` / `RefreshToken`), подходит для AiQueue. В клиенте
добавить геттер `aiQueueAuthQuery()` который возвращает `?token=<...>`
из текущего `UserSimplePreferences.getAccessToken()`.

### Формат запроса

```http
POST https://aiqueue.ru.tuna.am/?token=<jwt>
Content-Type: text/plain;charset=UTF-8

{"id": <chatId>, "method": "AiQueue.<method>", "params": {...}}
```

⚠️ **`id` ≠ обычный JSON-RPC id.** Здесь `id` это **chatId** — стабильный
идентификатор истории чата на стороне сервера. Менять `id` = открыть
новый чат. Повторять `id` = добавить ещё один turn в существующую историю.

### Формат ответа

Все методы возвращают единую обёртку:
```json
{
  "id": <тот же chatId>,
  "response": "<строка с кратким маркером>",
  "fromMethod": "AiQueue.<method>",
  "result": { ... },           // полезная нагрузка
  "errors": [ ... ]            // массив ошибок, [] если ок
}
```

Признак успеха: `errors` пустой массив. На любой непустой `errors` клиент
должен трактовать как ошибку (даже если HTTP 200).

## 3. Концепции

### chatId

- 64-bit integer, генерируется клиентом.
- Уникален в рамках всего приложения (не повторяется между отчётами).
- Привязан к одному элементу автомобиля. Один элемент = один chatId.
- Хранится локально в attached-к-отчёту структуре:
  `{ "<elementKey>": <chatId> }`. См. §6 «Storage на клиенте».
- Генерация: `DateTime.now().microsecondsSinceEpoch` гарантированно
  уникален в рамках одного устройства; коллизия с серверной историей
  невозможна — она не глобальная, scoped по userId внутри NATS KV.

### cliche

Шаблон промпта для AI. Содержит инструкции «как формализовать заметку».
В клиентском коде хранится в виде структуры, при отправке сериализуется в
строку. Должен включать:

1. **Контекст элемента** — название элемента осмотра + раздел
   (`{section_name} · {element_name}`).
2. **Список тегов замечаний/повреждений** — какие аспекты пользователь
   уже отметил чек-боксами (например, «Сколы», «Скрытая коррозия»).
3. **Шаблонный плейсхолдер `{text}`** — место, куда сервер подставит
   `params.text` пользователя.
4. **Желаемый формат ответа** — длина, тон, структура (списком vs
   абзацем), упоминать ли VIN.

**Минимальный пример cliche** для per-element:
```
Ты — помощник автоподборщика. Сформулируй замечание по элементу
осмотра «{element}» (раздел: {section}).

Уже отмеченные теги: {tags}.
Сырая заметка пользователя: {text}.

Ответ — одно предложение, нейтральный тон, без воды. Если в заметке
противоречие с тегами — указать это.
```

Где `{element}`, `{section}`, `{tags}` — клиент подставляет до отправки.
`{text}` — оставляет, сервер сам подставит из `params.text`.

### fileUrls

Массив **presigned S3 URL** уже загруженных файлов (фото / аудио). Сервер
передаёт их в multimodal AI-запрос как `image_url` parts.

**Pre-condition**: файл должен быть успешно загружен в S3 *до* вызова
AiQueue. Текущий пайплайн загрузки (`storage_api.dart` →
`Storage.PrepareSpecialistReport` → S3 multipart upload) выдаёт
presigned URL; они и попадают в `fileUrls`. Срок жизни — равен TTL
presigned URL в S3 настройках бэка (обычно 1–24 часа).

### model

Опциональный параметр. Доступные значения берутся из `AiQueue.Models`:
сейчас `gpt-5.5`, `gpt-5.4` (default — `gpt-5.4`).

Клиент **не должен** хардкодить список моделей — на запуск приложения
кэшировать результат `AiQueue.Models` (TTL 1 час), на dropdown выбора
модели в dev-меню использовать кэш.

### History TTL

- Хранится 6 часов (env-настраиваемо).
- Каждая запись (новый turn в `ChatCompletions`) **продлевает** TTL.
- Чтение (`GetChatHistories`) **не продлевает**.
- Если клиент собирает summary через 7+ часов после последней записи в
  per-element чате — история уже стёрлась. Решение: вести summary в
  пределах рабочей сессии, или дублировать важный контекст в локальной
  draft-структуре.

## 4. Сценарий A — формализация заметки по элементу

### Шаги

```
[1] Юзер тапает «Помощник AI» рядом с полем заметки в editor'е элемента.
[2] Клиент:
    a. Берёт/генерирует chatId для (reportId, elementKey).
    b. Собирает cliche (раздел, элемент, теги, шаблон ответа).
    c. Берёт presigned URL уже загруженных медиа этого элемента.
    d. POST /?token=<jwt>  body: {id: chatId, method: "AiQueue.ChatCompletions", params: {...}}
[3] Получает result.text — отформатированный текст от AI.
[4] Показывает в UI с кнопками «Принять», «Уточнить», «Сбросить».
    - «Принять»  → подставляет текст в поле заметки, диалог не закрываем (чтобы можно было итерировать).
    - «Уточнить» → юзер пишет дополнение, клиент шлёт ещё ChatCompletions с тем же chatId, history продолжается.
    - «Сбросить» → AiQueue.ClearChatHistory(chatId) → следующий запрос с этим chatId стартует с нуля.
```

### Пример запроса

```http
POST https://aiqueue.ru.tuna.am/?token=eyJ...
Content-Type: text/plain;charset=UTF-8

{
  "id": 1745613920123456,
  "method": "AiQueue.ChatCompletions",
  "params": {
    "text": "капот вмятина 5см с краю + ржавчина пошла под ЛКП",
    "cliche": "Ты — помощник автоподборщика. Сформулируй замечание по элементу осмотра «Капот» (раздел: Кузов).\n\nУже отмеченные теги: «Вмятины», «ЛКП».\nСырая заметка пользователя: {text}.\n\nОтвет — одно предложение, нейтральный тон.",
    "fileUrls": [
      "https://s3.../bodyhood-photo-001.jpg?X-Amz-Algorithm=...",
      "https://s3.../bodyhood-audio-001.m4a?X-Amz-Algorithm=..."
    ],
    "model": "gpt-5.4"
  }
}
```

### Пример ответа (happy path)

```json
{
  "id": 1745613920123456,
  "response": "ok",
  "fromMethod": "AiQueue.ChatCompletions",
  "result": {
    "text": "На капоте вмятина ~5 см у края с очагом коррозии под ЛКП — требует ремонта."
  },
  "errors": []
}
```

### Сценарий уточнения (тот же chatId)

```json
{
  "id": 1745613920123456,
  "method": "AiQueue.ChatCompletions",
  "params": {
    "text": "добавь, что покраска уже одна была",
    "cliche": "<тот же шаблон что в шаге 1>"
  }
}
```

История на сервере уже знает первый turn — ответ будет с учётом контекста.

## 5. Сценарий B — итоговая заметка по отчёту

### Шаги

```
[1] Юзер на финальном экране отчёта тапает «Сгенерировать заключение».
[2] Клиент собирает все chatId из per-element записей этого отчёта.
[3] POST AiQueue.GetChatHistories с массивом ids.
[4] Получает map { "<chatId>": [<turns...>] }.
[5] Строит итоговый context-string по своим правилам — например:
    "## Капот\n• Замечание: ...\n## Двигатель\n• Замечание: ...\n..."
[6] Генерирует НОВЫЙ chatId (не переиспользует ни один из per-element).
    Сохраняет его как report.finalChatId.
[7] Готовит summary-cliche («Собери из заметок выше итоговое заключение
    по автомобилю с разделами Кузов / ТЧ / Электрика. Тон официальный,
    выводы по разделам отдельно.»).
[8] POST AiQueue.ChatCompletions с новым chatId, params.text = собранный
    context, params.cliche = summary-cliche.
[9] Получает итоговый текст, показывает в editor'е summary с возможностью
    редактирования.
```

### Пример GetChatHistories

```json
// request
{
  "id": 1745700000000001,
  "method": "AiQueue.GetChatHistories",
  "params": {
    "ids": [1745613920123456, 1745613920123457, 1745613920123458]
  }
}

// response (структура `chats` — map по строковому ключу chatId)
{
  "id": 1745700000000001,
  "fromMethod": "AiQueue.GetChatHistories",
  "result": {
    "chats": {
      "1745613920123456": [
        {"role": "user",      "content": "..."},
        {"role": "assistant", "content": "..."}
      ],
      "1745613920123457": [...],
      "1745613920123458": [...]
    }
  },
  "errors": []
}
```

⚠️ Если у какого-то chatId TTL истёк — этот ключ может отсутствовать в
`chats` или содержать пустой массив. Клиент должен обрабатывать оба
варианта мягко (skip + warning в UI: «История по элементу X истекла,
используем только текущий черновик»).

### Пример summary-запроса

```json
{
  "id": 1745700000000099,
  "method": "AiQueue.ChatCompletions",
  "params": {
    "text": "## Кузов\n• Капот: вмятина 5см с коррозией.\n• Крыло: царапина.\n## Двигатель\n• Расход масла повышен.\n## ...",
    "cliche": "Ты — автомобильный эксперт. Собери итоговое заключение по отчёту осмотра. Структура: разделы (Кузов / Двигатель / Тех. состояние / Юр. чистота). Тон официальный, выводы по разделам — отдельно. Финал — общая рекомендация (Покупать / Не покупать / Покупать с торгом). Заметки специалиста ниже:\n\n{text}",
    "model": "gpt-5.4"
  }
}
```

## 6. Storage на клиенте

В draft'е отчёта (см. `SparkJoyStorage.upsertDraft`) добавить новое поле:

```dart
'aiQueueChats': {
  // per-element: ключ — mediaGroupKey + index элемента
  '<elementKey>': <chatIdInt>,
  // финальный summary chat
  '__final__': <chatIdInt>?,
}
```

Правила:
- Никогда не удалять chatId из этой map'ы вручную (даже если юзер сбросил
  AI-помощник через `ClearChatHistory` — chatId остаётся как «использованный»).
- При удалении draft'а / завершении отчёта — chatId'ы можно отбросить,
  они на сервере истекут сами.
- При reopen draft'а — карта восстанавливается из `_loadDraftIntoState`.
  Если соответствующий chatId найден на сервере (ChatCompletions с тем
  же id вернёт продолжение истории) — реюзаем; если TTL истёк, сервер
  начнёт новый чат с тем же id, что для нас норм.

## 7. Ошибки

### Сетевые / транспортные

| Симптом | Действие |
|---|---|
| HTTP 4xx (auth) | `clearAuthTokens` + redirect на login (как для Storage RPC, см. `_postRpc`) |
| HTTP 5xx | Retry с экспоненциальным backoff (макс 3 попытки) |
| Timeout | Snackbar «AI-помощник не отвечает, попробуйте ещё раз», cancel-button в UI |

### Доменные

`errors[]` непустой → каждая ошибка имеет `code` + `message`. Кодов сейчас
в спеке нет (TODO для бэка — добавить таблицу), пока показываем юзеру
generic «AI-помощник вернул ошибку: {message}». Полный JSON ошибок логируем
в `developer.log` под именем `AiQueue.error` для диагностики.

## 8. Производительность и UX

- **Не блокируем UI**. Запрос делать в `compute` или async task; пока
  идёт — показывать в диалоге spinner с кнопкой Cancel.
- **Cancel** = закрыть диалог + игнорировать пришедший ответ; chatId
  не удалять (сервер уже принял turn, история есть).
- **Дебаунс** на «Уточнить»: не позволять второй запрос пока первый в
  полёте по этому же chatId, иначе порядок turns в истории
  непредсказуем.
- **Кэш моделей**: `AiQueue.Models` дёргать один раз на старт сессии,
  держать в памяти. Не на каждый клик.

## 9. Что нужно реализовать на клиенте

1. Новый api-клиент `lib/data/api/ai_queue_api.dart` (или внутри
   `storage_api.dart` как отдельный класс) с методами:
   - `chatCompletions({chatId, text, cliche, fileUrls, model})`
   - `clearChatHistory(chatId)`
   - `getChatHistories(ids)`
   - `models()` (с TTL-кэшем)
2. Сервис `lib/data/services/spark_joy_ai_assistant_service.dart`:
   - Управление chatId'ами (генерация, мапинг element → chatId)
   - Сборка cliche по элементу
   - Сборка summary-context из истории
3. Расширение draft-схемы `aiQueueChats` в `spark_joy_storage_helpers.dart`.
4. UI:
   - Кнопка «AI-помощник» в editor'е элемента осмотра.
   - Диалог с состояниями: idle → loading → result → editing → applied.
   - Кнопка «Сгенерировать заключение» на summary-шаге, отдельный модал.
5. Тесты:
   - Unit: cliche-builder для разных секций.
   - Unit: context-builder из mock-историй.
   - Widget: диалог состояний + cancel.

## 10. Открытые вопросы к бэк-разрабу

1. **Codes ошибок** — есть ли таблица error codes для `errors[]`? Сейчас
   клиент не знает, как отличить «модель занята» от «cliche слишком
   длинный» от «токен истёк».
2. **Лимиты** — есть ли rate limit на ChatCompletions? Нужно ли ставить
   ограничитель на клиенте?
3. **Размер cliche** — есть ли максимум? И есть ли максимум на text?
   Сейчас фронт не валидирует длину.
4. **Размер fileUrls** — сколько URL за один запрос максимум? Что
   будет если передать 50 фото?
5. **TTL** — `AI_QUEUE_CHAT_HISTORY_TTL_HOURS=6` — это финальное
   значение для прода, или dev-значение? Для итоговой заметки 6 часов
   мало, если осмотр займёт день.
6. **Доступ Storage** — на каком endpoint теперь живёт Storage.* (тэги,
   отчёты, файлы)? `https://podbor-av.ru.tuna.am` всё ещё актуален или
   тоже переехал?
7. **`Content-Type: text/plain`** — это намеренно (избегаем CORS preflight?)
   или просто quirk? Нужно ли клиенту обрабатывать как JSON в Dart-
   парсере несмотря на text/plain?
